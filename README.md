# TROPOMI PMC Explorer

Статическое клиентское приложение для локального исследования Sentinel-5P TROPOMI Level‑1B RA_BD1. Реализованы инспектор NetCDF4/HDF5, геолокация и экспериментальное обнаружение вероятных PMC с экспортом GeoJSON.

## Приватность и архитектура

Выбранный `.nc` не загружается в сеть. Браузер передаёт объект `File` модульному Web Worker. `h5wasm` монтирует файл через Emscripten `WORKERFS`, поэтому HDF5 использует произвольный доступ к локальному Blob, а главный UI-поток получает только прогресс, метаданные и небольшой GeoJSON. Backend, API routes, Python, Docker и Netlify Functions отсутствуют.

MapLibre загружается только в client component. Подложка OpenStreetMap не требует токена; при её использовании браузер запрашивает только тайлы карты, не содержимое научного файла.

## Инспектор и геолокация

Инспектор рекурсивно обходит groups и datasets, показывает shape/dtype/attributes и оценивает кандидатов по имени, пути и метаданным. Код не привязан к одному фиксированному пути. Орбитальный полигон строится по внешнему контуру фактической сетки координат; GeoJSON использует порядок `[longitude, latitude]`, нормализует долготу и пропускает недопустимые координаты.

## Pipeline PMC

Приложение выбирает ближайшие каналы 283,0, 287,0 и 291,5 нм отдельно для каждого detector row. Radiance читается блоками по 12 scanline. Для каждого cross-track ряда строится полином четвёртой степени от SZA; яркие положительные выбросы исключаются, и оценка повторяется до пяти раз. Шум оценивается через `1.4826 × MAD` в SZA-интервалах 0,25°. Применяются трёхканальные критерии статьи и 8-связные компоненты с минимальным размером кластера 3 пикселя по умолчанию — одиночные несвязные пиксели-выбросы не считаются PMC-детекцией.

Morphological closing/opening доступны как переключатели в UI, но выключены по умолчанию. Замер на реальных орбитах: `minimumClusterSize: 3` снижает суммарную площадь примерно на 15% (корректно отсекает шум), а `closing` — наоборот, увеличивает её на 25–30% (дилатация+эрозия заполняет мелкие пробелы между соседними детекциями пикселями, которые сами порог не проходили). Поскольку цель — не завышать площадь сверх фактических пересечений порога, closing по умолчанию отключён.

Геолокация PMC-пикселей и их corner-координат дополнительно сдвигается параллактической поправкой на высоту облачного слоя ~83 км (`lib/geo/parallax.ts`): смещение = height × tan(viewing zenith angle) вдоль viewing azimuth. Это нужно, чтобы одно и то же облако, увиденное перекрывающимися соседними орбитами под разными углами визирования, при слиянии суточной мозаики сходилось в одну область, а не удваивало площадь. Контур орбитального следа и широтные/сезонные фильтры используют исходную (неисправленную) геолокацию — параллакс относится только к положению облака, а не к треку спутника.

`detectionScore` — прозрачный эвристический ранг по S/N, размеру компонента и спектральному спаду. Это не вероятность.

## Научные ограничения

Без отдельного IR_UVN приложение работает с residual radiance, а не residual albedo. Это приближение статьи и может давать ложноположительные результаты. Порог MAD внутри текущей орбиты заменяет опубликованный порог, построенный по межсезонной cloud-free выборке. Поэтому результат называется «вероятные PMC», а не подтверждённые облака.

**Площадь в км² по бинарному порогу не сравнима с другими инструментами (AIM/CIPS и т.п.).** Измерено на реальных corner-координатах: нативный пиксель TROPOMI Band 1 (UV, каналы 283/287/291,5 нм) занимает ~140–210 км², а после обязательного по статье биннинга 2×2/2×3 — ~650–1250 км². Это на 1–2 порядка грубее, чем у приборов, спроектированных специально для PMC (у CIPS нативный пиксель ~25 км²). Бинарный подсчёт («любая детекция красит весь грубый пиксель на 100%») поэтому даёт завышенную площадь — это не ошибка равновеликой проекции/объединения полигонов в `lib/geo/pmc-area.ts` (она верна), а следствие грубого разрешения канала в сочетании с бинарным порогом.

Это чинится: `featureFootprintAreaKm2()` в `lib/geo/pmc-area.ts` даёт площадь конкретного footprint-а, а «ФРАКЦИОННАЯ ПЛОЩАДЬ» в интерфейсе умножает её на `detectionScore` (0…1, доля яркости от опорного значения 30×10⁻⁶ sr⁻¹ — та же константа, что статья использует для Figure 10) вместо счёта пикселя целиком при любом превышении порога. На реальной орбите это даёт ~41% от бинарной площади (213 825 → 87 960 км² при среднем detectionScore ≈ 0,39) — грубая, но принципиально верная линейная модель sub-pixel cloud fraction, а не произвольная поправка. Константа 30×10⁻⁶ как «полностью облачно» и линейное смешение сигнала не откалиброваны независимо, поэтому это тоже приближение, но качественно верное, в отличие от бинарного счёта.

Сама статья Wu et al. по той же причине не публикует площадь в км² — только occurrence frequency в процентах (их Figure 15), которая вообще не зависит от размера пикселя. Она остаётся самой надёжной метрикой для сравнения с литературой; в интерфейсе occurrence % и фракционная площадь — главные выделенные метрики, бинарная площадь показана, но визуально понижена.

Научная основа: *Detection of Polar Mesospheric Clouds with TROPOMI*, Remote Sensing 18(10), 1599.

## Браузеры и память

Рекомендуются актуальные 64-битные Chrome или Edge. Метаданные читаются быстро, но извлечение двух полных координатных datasets может потребовать десятки мегабайт памяти. Worker можно отменить между этапами, однако активный синхронный вызов HDF5 нельзя прервать посередине.
